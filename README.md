# memodeAR プロトタイプ

## ファイル構成
```
index.html               … AR表示ページ（QRコードの遷移先はここ）
input.html                … メモ入力ページ（作成／更新／削除の3択メニュー方式）
manifest.json              … ホーム画面追加（PWA）用設定
marker.mind                … 仮のマーカーデータ（要差し替え・後述）
assets/
  style.css                … 共通デザイン（ロゴと同じ枠：frame-box）
  frame.js                 … frame-box に4隅の装飾パーツを自動追加するスクリプト
  firebase-config.js        … Firebaseの接続設定（firebaseConfigをご自身で入力）
  cloud-store.js            … Firebase Realtime Database経由でメモを読み書きする共通処理
  img/memodeAR_logo.png     … いただいたロゴ画像
  icons/memodeAR_aicon.png  … ホーム画面アイコン（暫定、ロゴを流用）
```

## 今回の主な変更点

### QRの遷移先をAR画面に変更
`index.html` の中身をAR表示ページに置き換えました。
これまであった「入力／AR表示を選ぶ案内ページ」は廃止しています。
入力ページには直接 `input.html` としてアクセスしてください
（メモの持ち主の方がブックマーク等で開く想定です）。

### 入力ページを3択メニュー方式に変更
`input.html` を開くと、まず以下の3つのボタンが表示されます。
- **メモを作成** → 空の入力フォームが開き、保存すると新規メモとして履歴に追加され、
  同時にAR表示用として設定されます
- **メモを更新** → 過去の履歴（最大5件）が一覧表示され、選んだメモを編集できます。
  履歴がなければ「履歴がまだありません」と表示します
- **メモを削除** → 現在AR表示に設定されているメモの内容を表示し、確認のうえ削除します。
  削除できるメモがなければ「削除できるメモがありません」と表示します

各画面には「‹ 戻る」ボタンを用意しています。
また「memodeAR」というタイトル文字は入力ページから削除しました。

### 「メモに設定しても保存・削除ができない」不具合の修正
以前の実装は「メモを作成」ボタンで履歴に追加する操作と、「メモに設定」でAR表示用に
反映する操作が別々になっており、後者だけ押すと履歴に何も残らず、
結果として更新・削除の対象にできない、という不具合がありました。
今回、**保存操作を1つに統合**し、作成・更新のどちらも「履歴への保存」と
「AR表示用への反映」を必ず同時に行うようにしたので、この問題は解消しているはずです。

## アイコンが404になる件について
実際に `https://shiguretei-amagasa.github.io/memo_de_AR/assets/icons/memodeAR_aicon.png` に
直接アクセスして確認したところ、現時点でもまだ404でした。
ファイル自体はこちらの一式には正しく含まれているので、GitHub Pages側に
まだ反映されていない可能性が高いです。以下をご確認ください。
- GitHubリポジトリの中身を直接見て、`assets/icons/memodeAR_aicon.png` が
  実際にその場所に存在しているか（フォルダごとドラッグ＆アップロードした場合、
  空フォルダやファイルが抜け落ちることがあります）
- ファイル名・フォルダ名の大文字小文字が完全に一致しているか
  （GitHub PagesはLinuxベースのため、Macと違い大文字・小文字を区別します）
- GitHub Pagesの反映には数分ほどタイムラグが出ることがあるので、
  プッシュ直後であれば少し時間をおいて再確認する

## 入力したメモがAR側に表示されない件について

なお、`assets/firebase-config.js` の設定がまだの場合は動作しませんのでご注意ください。

## バージョン確認について（今後のすれ違い防止）
「直したはずなのに直っていない」というやり取りが続いているため、
`index.html` と `input.html` の `<head>` 内に `<!-- build: v5 -->` という
目印のコメントを入れ、CSS/JSの読み込みにも `?v=5` を付けました。
公開先のページで「ページのソースを表示」し、この番号が
今回お渡ししたものと一致しているかを見れば、最新版が確実に反映されているか
その場で確認できます。次回以降、番号が古いままであれば
「まだ公開側に反映されていない」と判断できます。

## AR画面が真っ暗になる件について
ARnksy・LettARの過去のやり取りをもとに確認したところ、原因が特定できました。

**原因**：`html, body { background: #000; }`（黒背景）が、カメラ映像を映す`<video>`要素が
何らかの理由で正しく最前面に重なっていない場合に、その裏側を黒で埋め尽くしてしまい、
「カメラは起動しているのに何も映っていないように見える」状態を作っていました。
LettARの時と全く同じパターンです。

**対応**：`index.html` の背景を `background: transparent;` に変更しました。
これで、万一カメラ映像側の重なりに問題があった場合でも「真っ黒で覆い隠す」のではなく
「何も表示されない」状態になるため、問題が起きているかどうかが分かりやすくなります。
（`arError` イベントの検知・8秒タイムアウトの診断表示は前回同様そのまま残しています）

なお、コンソールに出ていた `useLegacyLights has been deprecated` は
three.js側の仕様変更に関する警告であり、エラーではないため黒画面の直接の原因ではありません。

## 「モーションセンサーへのアクセスが必要です」の表示について
これはOS標準のダイアログではなく、A-Frameというライブラリが自前で表示していた
英語の確認画面でした。今回の画像マーカー式AR（イラスト認識）では
コンパスやジャイロのデータを実際には使っていないため、翻訳するのではなく
この許可要求自体を `index.html` 側で無効化しました
（`device-orientation-permission-ui="enabled: false"`）。


原因が判明しました。`assets/style.css` 内で、4隅の装飾パーツ用に書いていた
`[class^="fb-"]`（"fb-"で始まるクラス名すべてに一致）というセレクタが、
本来は装飾パーツ専用のつもりが、実際の中身を囲む `.fb-content` にも
意図せず一致してしまっていました。
その結果、`.fb-content` にまで `position: absolute` と `pointer-events: none` が
適用され、
- 中身が通常のレイアウトから外れて高さがつぶれる（＝3択メニューや履歴が
  デザインされていない・選択できないように見える）
- `pointer-events: none` が子要素（プルダウンや入力欄）にも継承され、
  クリックや入力を一切受け付けなくなる

という2つの不具合を同時に引き起こしていました。
今回、装飾パーツ用のセレクタを8つのクラス名を明示的に指定する形に修正し、
`.fb-content` に影響が及ばないようにしたので、解消しているはずです。

## 共通デザイン（ロゴの枠）について
いただいたロゴ画像の4隅を拡大して確認したところ、以下の構造になっていました。
- **左上・右下**：辺とは接触せず隙間をあけて角にフラッシュした小さな四角アクセント
- **右上・左下**：CSSの「単角丸み」テクニックによる大きな弧

これを `assets/style.css` の `.frame-box` として実装し直しました。
今回から、`class="frame-box"` を付けた要素に対して `assets/frame.js` が
自動的に4隅の装飾パーツを追加する仕組みにしたので、
どのページのどの要素に `frame-box` クラスを付けても同じ枠が再現されます。
太さ・丸みの半径・隙間の大きさは `style.css` 冒頭の
`--frame-width` / `--frame-notch` / `--frame-gap` / `--frame-radius` で調整できます。

## 複数端末対応（Firebase）について
PCで入力してスマホで読み取る、Aのスマホで入力してBのスマホで読み取る、
というテスト方法だと、`localStorage` 方式では原理的に動作しません
（`localStorage` はその端末・そのブラウザだけに閉じたデータ保存場所のため）。

当初はjsonbin.ioという簡易サービスで対応しましたが、
「APIキーをコードに直接書くのは抵抗がある」とのご要望を受けて、
Googleの「Firebase」（無料枠あり）のRealtime Databaseに切り替えました。

### jsonbin.ioとの違い（なぜAPIキー直書きの不安が解消するか）
jsonbin.ioの「X-Master-Key」は、そのアカウントの全データを読み書きできる
本物の秘密鍵で、コードに書くと誰でも読めてしまうものでした。
一方、Firebaseの`firebaseConfig`に含まれる`apiKey`は、性質が異なり、
**公開されることを前提に設計された識別情報**です（Firebase公式もそう案内しています）。
実際のアクセス制御は、後述する「データベースのルール」の方で行うため、
`firebaseConfig`自体が漏れても、ルールさえ適切なら悪用されません。

### セットアップ手順（最初に1回だけ）
1. https://console.firebase.google.com でGoogleアカウントでログインし、
   新しいプロジェクトを作成する（無料）
2. 左メニューの「Realtime Database」を開き、データベースを作成する
   （ロケーションはお好みで、例：asia-southeast1）
3. 「ルール」タブを開き、以下の内容に書き換えて「公開」する
   ```json
   {
     "rules": {
       "memodeAR": {
         ".read": true,
         ".write": true
       }
     }
   }
   ```
   これにより、`memodeAR` というパスだけが誰でも読み書きできる状態になり、
   それ以外のパスは塞がれます（データベース全体を開放するより安全です）
4. 画面左上の「⚙️ プロジェクトの設定」→「全般」タブの一番下、
   「マイアプリ」で `</>`（ウェブ）アイコンをクリックしてアプリを登録すると、
   `firebaseConfig` の値一式が表示されるので、それをコピーする
5. `assets/firebase-config.js` を開き、コピーした値を
   それぞれの `""` の中に貼り付けて保存する

これで `input.html`（保存）と `index.html`（AR表示）が同じデータベースを
見に行くようになるので、どの端末の組み合わせでも動作するはずです。

### セキュリティについて
上記の通り`apiKey`自体は公開前提のものですが、手順3の
「ルール」を`true`/`true`のまま本格運用すると、**そのURLを知っている人なら
誰でも書き換え・削除ができてしまう**点は変わりません（jsonbin版と同程度の制約です）。
個人のプロトタイプとして試す範囲では問題ありませんが、将来的に他人にも
使われる想定になった場合は、Firebase Authentication（匿名ログインなど）を
組み合わせて、ルールをさらに絞り込むことをおすすめします。

## 動作の仕組み（試作段階）
- `input.html` で保存すると、内容がFirebase上の `/memodeAR` パスに
  `{ "active": {...}, "history": [...] }` という形で保存されます
- `index.html`（AR画面）はページを開くたびにこのパスを読み込んで表示します
- そのため、`assets/firebase-config.js` の設定さえ済んでいれば、
  **入力とAR表示を別の端末で行っても反映されます**
- 通信が発生するため、保存・読み込みには数百ミリ秒程度の時間がかかります

## 試す手順
1. 上記の「複数端末対応（Firebase）」のセットアップ手順を済ませる
2. `marker.mind` を実際のイラストからコンパイルしたデータに差し替える
3. フォルダごとHTTPS環境でホスティングし、`assets/` 一式（`firebase-config.js`を含む）を確実にプッシュする
4. どの端末でもよいので `input.html` を開き、「メモを作成」から内容を入力
5. 別の端末で `index.html`（QRの遷移先）を開き、マーカーにカメラをかざして表示を確認
